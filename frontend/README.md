# Stemora frontend

React 19, TypeScript (strict), Vite, Tailwind CSS v4, shadcn/ui on Base UI, React Router, TanStack Query, zustand, sonner. Dark theme only.

## Commands (pnpm)
| Command | What |
| --- | --- |
| `pnpm dev` | Dev server; `/api` proxied to `http://localhost:8080` |
| `pnpm dev:mock` | Dev server with an in-memory mock of the contract (`mock/plugin.ts`), no backend needed |
| `pnpm lint` | ESLint with `@shadcn/lint` design rules |
| `pnpm typecheck` | `tsc --noEmit` |
| `pnpm test` | Vitest (mixer/loop/peaks logic, upload chunking and retry, formatters) |
| `pnpm build` | Type-check and production build to `dist/` |
| `pnpm mock:audio` | Regenerate the 4 mock stems + peaks in `public/mock` (needs ffmpeg) |
| `pnpm splash` | Regenerate the iOS launch screens in `public/splash` and print their `<link>` tags for `index.html` (needs ImageMagick) |

## Mock mode
`pnpm dev:mock` serves the whole API from memory: seeded login `dev@stemora.test` / `password` (admin), one ready song with four 20 s generated stems, one processing, one failed, plus 40 filler ready songs to page through. Uploads hit fake presigned `PUT /mock-upload/...` URLs and then run a ~16 s simulated job. `VITE_MOCK_FRESH=1` starts with zero users to try first-run bootstrap; invite token `invalid` shows the invalid-invite page. Like the backend, at most 2 songs import or process at once; the rest wait as `pending` and start in order. Link imports walk through the backend's stages (waiting, probing, a ~6 s simulated download, storing) before the job starts; links containing `broken` fail the preview, `long` preview as too long, and `fail` fail mid-import. Spotify track links open the "Is this the song?" picker (`nomatch` in the link: no matches); Spotify albums/playlists and YouTube/SoundCloud playlists open the song chooser with 14 mock songs.

## Structure
- `src/player/engine.ts`: framework-free Web Audio engine. All stems start at one shared `ctx.currentTime` and offset (sample-accurate sync); seeking recreates sources; A-B loops use the sources' own `loopStart`/`loopEnd`; metronome clicks on the tempo map's beats. At the original speed and key the stems play straight from their buffers; otherwise they play through Signalsmith Stretch AudioWorklets (`signalsmith-stretch`, WASM), one per stem so each can have its own key (stems left out of a key change keep their original pitch), each holding its own copy of its stem's PCM and changing tempo and key in a single pass with no `playbackRate` resampling. Every node gets the same schedule and derives its read position from the audio clock through it, so the stems stay in sync; each feeds its stem's gain so the mixer stays live. The nodes and their PCM copies are built only the first time speed or key leaves the original; the metronome skips it, and the song's end is marked on the audio clock. Pure logic (mixer/solo/loop maths, peaks, tempo dial, chord transposition, which stems follow the key) lives in `mixer.ts` / `peaks.ts` / `tempo.ts` / `analysis.ts` / `transpose.ts` and is unit-tested.
- `src/player/store.ts`: zustand store driving the engine; `ui/` holds the player components, `mediaSession.ts` and `keepAlive.ts` handle lock-screen controls and background playback (best effort, a silent looping `<audio>` keeps iOS/Android treating the page as media).
- `src/lib/upload.ts`: single PUT or 16 MiB multipart upload with per-part retry, ETag collection, then `POST /complete`.
- Processing (`/processing`, `src/pages/processing.tsx`, `src/lib/queue.ts`; `/queue` redirects there): everything in flight, with a count badge in the nav. It is called Processing rather than Queue so that "queue" never means what plays next (see `docs/playback.md`). The queue itself lives on the server (songs wait as `pending` until one of the user's slots frees up, see `docs/contract.md`), so it is the same on every device and keeps going with the app closed. Only file transfers are device-local: `src/lib/uploads.ts` keeps them outside React so they survive navigation, and warns before closing the tab mid-upload. Links are pasted in bulk on the Upload page and join the queue right away. Spotify links and playlists (`src/lib/links.ts` decides which) are looked up first: a Spotify song asks which YouTube upload to use, a playlist or album which songs to add (`src/components/app/import-choices.tsx`, in a `ResponsiveDialog`).
- `src/components/ui`: shadcn components (Base UI style `base-nova`).
- Responsive overlays (`src/components/app`): `ActionMenu` (actions, separators and single-choice radio groups) and `ResponsivePanel` (a titled panel of controls) render a dropdown or popover on desktop and a swipeable bottom drawer on mobile. App code uses them instead of the Popover/DropdownMenu/Drawer primitives (enforced by lint). On touch screens (`pointer-coarse`), the small `Button`/`Toggle` sizes grow to 44px, and lint stops call sites from overriding a Button's height.
- Theme tokens, gradients, safe-area utilities and motion (`ease-spring`, `animate-page`, `stagger-children`, `animate-sheet-in/out`, `pressable`, `sheet-drag`): `src/index.css`. Everything respects `prefers-reduced-motion`.

## Command palette
Every keyboard shortcut is a command (`src/lib/commands.ts`), and Ctrl/⌘+K (or Ctrl/⌘+Shift+P, or "Search commands" in the sidebar) opens the palette (`src/components/app/command-palette.tsx`, cmdk) listing every command available right now with its shortcut, so whatever the keyboard can do can also be searched for and run from there. Components register commands while mounted with `useCommands(() => [...], level)`: the factory runs on each key press and palette open, never during render, so commands read current state, and `enabled()` hides a command and lets its key fall through. Deeper levels (`app` < `page` < `view`) win a shared key and are listed first; the shell adds Go to and Sign out, the player its playback, mixer, view and song commands (`use-player-commands.ts`), the desktop tempo editor its own. One window listener runs them. It leaves fields, open dialogs and menus alone, Space/Enter to focused buttons and arrows to sliders and tabs, and matches letters and digits by physical key, so shortcuts work on any keyboard layout. Lint blocks other window key listeners; keys a focused widget handles itself (tick dial arrows, tap tempo) stay in its `onKeyDown`.

## Native feel
- Page transitions: switching bottom-nav pages fades through with React `<ViewTransition>` (`src/components/app/page-transition.tsx`, CSS in `index.css`). The player route is skipped (it slides as a sheet), and so is an iOS back swipe that the browser already animated. Browser back/forward does not animate: React flushes `popstate` updates synchronously.
- Library: search, sort (`?q=&sort=` in the URL, so reloads and back keep them) and a grid/list toggle (remembered per browser); pages of 30 load as you scroll (`use-in-view.ts`, with a Load more fallback). Pull down at the top to refresh (`use-pull-to-refresh.ts`); swipe a song left to reveal Delete, or all the way to delete it after confirming (`use-swipe-action.ts`, touch only).
- Status bar: `theme-color` matches the page background, and full-bleed sheets (player, sign-in) tint it with `useThemeColor`.
- Installed app: iOS launch screens, no text selection outside inputs, no link callouts, and no browser pull-to-refresh.

## Now playing
The loaded song outlives the player sheet. `PlaybackHost` (`src/player/ui/playback-host.tsx`), mounted once for a signed-in user above the routes, keeps saving the song's settings and tempo map and drives the lock-screen controls; signing out unmounts it and stops playback. Closing the sheet goes back to the page it was opened from (or the Library after a direct load) and the song keeps playing in the **mini player** (`mini-player.tsx`), rendered by the app shell in the bottom nav's glass: above the nav on phones (`bottom-mini`, with `pb-nav-mini` room below the page), at the bottom of the main area on desktop. Tap it to reopen the player, which picks up the loaded song without reloading; its X stops and unloads. While it shows, Space plays/pauses from any page (app-level commands). Deleting or reprocessing the loaded song stops it.

## Playback settings
Each song keeps its playback settings on the server (`src/player/settings.ts`, `PUT /api/songs/{id}/settings`, see `docs/playback.md`): the mixer, speed, key (and its switch), which stems follow the key, the metronome click and its sound. They arrive with the song (`SongDetail.settings`), so the player opens with them and nothing waits on another request. Changes apply at once and are saved behind the UI (`use-settings-sync.ts`, `createSyncedSaver` with `keepOnError`): a failed save never rolls back what you hear; the set stays in localStorage and goes out again with the next change, when the browser is back online, or the next time the song opens. A song with no server settings starts from the mixer older versions kept in this browser (moved to the server, then removed locally), else from defaults with this browser's last stems-that-follow-the-key and click sound.

## Tempo map
Every song has a tempo map (`src/player/tempo-map.ts`, saved per song with `PUT /api/songs/{id}/tempo-markers`): markers that each start a bar, either **manual** (BPM in the time signature's beat note, so 6/8 at 120 is 120 eighths a minute) or **auto** (the detected beats from the analysis). A new song starts with one auto marker at 0:00. A marker right after a manual one is locked to its grid: it sits a whole number of beats later, and moves with it when that marker's tempo or position changes; a marker after an auto one is free. A manual marker can carry a click pattern (`clicks`): a column per beat of the bar, each split into 1-8 evenly spaced clicks (the beat first) that are accent, normal or muted, edited Impulse-style (tap a dot to cycle it, − / + above and below a column for that beat, the outer ones for every beat; `src/player/ui/metronome/`). Without one it clicks every beat, accenting beat 1; an auto marker always clicks the detected beats, accenting detected downbeats. The click sound comes from the registry in `click-sounds.ts` (only "Classic" so far; a sound may decode audio files in `load`) and is part of the song's playback settings. The map's beat grid drives the metronome (clicks scheduled on the audio clock through speed and loop, `clicks.ts`), the chord chart and the drum notation (bars in their real meter, `\ts(6 8)`). "Export tempo map (MIDI)" in the song menu writes that grid as a Standard MIDI File (`src/player/midi.ts`: format 1, one conductor track with time signatures, tempos and section markers, no click) for a DAW: each beat lasts until the next, so a manual stretch is one tempo event and detected beats one per beat, never drifting more than 50 µs; the time before the first beat becomes a pickup, and the song's last, cut-off bar keeps the meter before it.

The **Tempo editor** (`src/player/ui/tempo-editor/`) draws the ruler (bars, clock, loop strip), the tempo lane and the four stems' real waveforms (min/max pyramid from the decoded PCM, `waveform-data.ts`; single samples when zoomed far in) on the beat grid; auto grid lines are dashed. Desktop: wheel scrolls, Ctrl/⌘+wheel or a trackpad pinch zooms at the pointer, Alt+wheel scales the waveforms; click to locate, drag the ruler's top strip for a loop, drag markers (snapping and ripple live), double-click the tempo lane to add one; the info line above edits the marker being played (or the one clicked): kind, BPM (↑/↓, Shift, Alt), time signature (type `6/8`, or pick), detected tempo, delete. Phones keep the cursor in the middle: drag the song under it (with momentum), pinch to zoom around it, add a marker at the cursor or move the current one there, and edit it in a drawer. Edits are undoable.

## Player workspace
Every view shares one skeleton (`src/player/ui/workspace.tsx`): a toolbar strip (`WorkspaceToolbar`, one frame for every view's tools) over a content panel with the same radius and border. Switching views only swaps what is inside them with a short fade (`Swap`, `animate-swap`), so nothing moves or resizes. The tempo editor renders its tools into the strip through a portal; the practice tools (`ChartToolbar`) and the mixer header (`MixerTools`) render there directly. Sub-switches inside a toolbar (Chords | Drums, Auto | Manual) use the quieter `pill` tabs variant; the view switch uses `workspace`.

## Mobile player
Three tabs that fit the screen without scrolling the page, each with its tools in the toolbar strip above the content: **Mixer** (four stem rows with mute, volume, solo and a menu; "All stems" in the strip clears every mute and solo), **Tempo** (the tempo editor) and **Practice** (the Chords / Drums chart). The transport row opens two `ResponsivePanel`s (drawers on mobile, popovers on desktop) with a swipeable tick dial: **Metronome** (click on/off in the header, a `‹ ›` navigator that seeks between tempo markers and shows the one under the playhead, then two tabs: **Click**, the marker's click pattern and the click sound, and **Speed**, the playback speed in BPM of the tempo under the playhead when there is one, else percent, 50-150 %; the speed is one multiplier for every section) and **Key**, laid out the same way (a switch in the header that plays the original key without losing the dial, for A/B comparison; a headline with the change heard and the analysed key it starts from; the ±12 semitone dial; and a **Stems** setting choosing which stems follow the key, drums left out by default). Stems that are transposed show the change next to their name in the mixer, and each stem's menu has "Follow song key". Both panels are built from `PanelHeadline` and `PanelSetting` (`src/components/app/panel-parts.tsx`), so a new panel of this kind lines up with them. The full preset-chip row is shown only on desktop. Swipe the grab bar or header down to close the player (`use-sheet-drag.ts`); closing only hides it (see Now playing).

## Drum notation
The Drums chart (`src/player/ui/drum-notation.tsx`) draws the quantised drum hits with alphaTab in two voices (hands stems up, kick stems down) and highlights the notes being played; while paused, the beat under the playhead stays marked, so tapping a note picks it. The settings panel (a drawer on phones) holds the grid, triplets, bars per row and a light/dark sheet (per browser, `drums/notation-prefs.ts`). The line break button (desktop: B) starts a new row at the current bar and marks it with a dashed barline at the end of the bar before; breaks belong to the song and are saved on the server (`PUT /api/songs/{id}/drum-breaks`) behind an optimistic update (`drums/use-drum-breaks.ts`). They are stored as the start times of their bars, so a tempo map change moves each to the bar line now nearest it (within half a bar, `drums/breaks.ts`); any left without one are removed with an Undo toast, and undoing the tempo change brings them back. Breaks saved as bar indices by older versions are converted on first open. On a phone with a fixed bars-per-row the sheet keeps a readable width and scrolls both ways; pinch to zoom (`use-pinch-zoom.ts`). If drawing fails or stalls, a Retry button rebuilds alphaTab (and refetches its font).

## Desktop player
The Tempo | Practice switch (V) sits at the top left, in line with the toolbar strip, above the mixer. The mixer column keeps the same place in both views: a header as tall as the editor's ruler and tempo lane (`h-15` = `HEADER_H`), then the stem rows, which in Tempo line up with the editor's lanes.

Shortcuts (all listed with their keys in the command palette, Ctrl/⌘+K): Space play/pause, Left/Right skip 10 s (Shift: 30 s), 1-4 pick a stem, M mute it, S solo it, L cycle loop (set A, set B, clear), V Tempo/Practice, Home restart. Practice: C switch chords/drums, B line break in the drum notation. Tempo editor: G/H zoom out/in, Shift+F whole song, F follow playback, T add a marker, Delete remove it, Enter edit its BPM, Esc release the selection, Shift+N/Shift+B next/previous marker, Ctrl/⌘+Left/Right nudge it (1 ms, Shift 10 ms, a beat when locked), Ctrl/⌘+Z undo, Ctrl/⌘+Shift+Z redo.

## Deployment
`Dockerfile` builds the SPA and serves it with nginx (`nginx.conf`): history fallback, gzip, long cache for `/assets`, no-cache for `sw.js`, and `location /api/` proxied to `http://backend:8080` (1 MB body limit; files go directly to R2). The R2 bucket CORS must allow `PUT` from the site origin and **expose the `ETag` header**, otherwise multipart uploads cannot complete.

## Notes
- iOS: audio starts from the first Play tap (AudioContext resume).
- PWA: `vite-plugin-pwa` (generateSW) precaches the app shell, so the installed app opens offline and shows a "Can't reach Stemora" screen instead of bouncing to login. `/api` and the presigned stem URLs are never cached, so songs still need a connection. `public/manifest.webmanifest` stays the manifest source. A new deploy shows a Reload toast (`src/components/app/pwa.tsx`; checks hourly and when the app returns to the foreground). If rendering crashes (typically an old cached build meeting a newer API), `src/components/app/error-boundary.tsx` shows a crash screen that activates a waiting or newly found service worker and reloads into it, since the toast cannot show once the app is down. The Account page shows the build time with a Check for updates button (`src/lib/pwa-update.ts`) and offers Install (Chromium prompt, or Safari's Add to Home Screen hint). The service worker only runs in `pnpm build`/`pnpm preview`, not in `pnpm dev`.
- Peaks come from `peaks_url`; if missing they are computed from the decoded audio.
